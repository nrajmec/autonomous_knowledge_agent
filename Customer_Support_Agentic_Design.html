UDA-Hub — Universal Decision Agent

A hand-built LangGraph multi-agent system that reads a CultPass support ticket, classifies it, routes it to a specialized resolver, grounds its answer in a knowledge base and the customer's own history, and either resolves or escalates it — with full state, session, and long-term memory throughout.

LangGraph StateGraph 8 agents + 2 system nodes Supervisor pattern FastMCP · 2 servers RAG · cosine similarity SQLite · SQLAlchemy gpt-4o-mini 97 tests
01 — Overview

What this system does

CultPass is a subscription cultural-experiences platform. When a customer writes in — "I can't log in," "I want to upgrade my plan," "cancel my reservation" — UDA-Hub takes that raw ticket text plus a bit of metadata (channel, account, customer id) and runs it through a fixed pipeline: load context → classify → route → resolve or escalate → persist. The interesting engineering is entirely in how that pipeline is built: every node and edge is hand-wired as an explicit LangGraph StateGraph — no create_react_agent, no langgraph_supervisor — so the routing logic that decides a ticket's fate is fully visible in code, not hidden inside a prebuilt helper.

Classify & route

One LLM call commits a ticket to exactly one of five categories, plus urgency/sentiment/complexity and a hard-escalate flag. A pure rule-based Supervisor dispatches from there — no ambiguity left for an LLM to resolve at the routing step.

Resolve with tools

Five category resolvers share one hand-rolled tool-calling loop (bind → invoke → execute → feed back, bounded at 4 iterations) against real CultPass/UDA-Hub data — profile lookups, subscription changes, reservations, knowledge-base search.

Remember

Three distinct memory mechanisms: LangGraph's own session checkpointer, a custom long-term customer_memory table for preferences/resolutions, and a durable ticket/message history — each solving a different requirement.

02 — Architecture

Supervisor (hub-and-spoke) pattern

A single supervisor node is re-entered twice per ticket and inspects state to decide the next hop, via LangGraph's add_conditional_edges. On its first entry — right after classification, before any resolver has run — it either dispatches to one of five category resolvers or bypasses straight to Escalation on a hard business-rule flag. On its second entry — after a resolver has produced a draft — it evaluates that resolver's confidence and either sends the ticket to Finalize or redirects it to Escalation. It's the same function both times; it just reads different signals out of state depending on whether confidence has been set yet.

This is deliberately rule-based, not an LLM call: the Classifier has already been forced, via structured output, to commit to exactly one of five categories, so there's no remaining ambiguity for an LLM to resolve at the routing step itself — it's a table lookup plus a threshold check.

Implemented in agentic/workflow.py as a hand-built StateGraph: nodes added explicitly (graph.add_node(...) ×10), a single add_conditional_edges("supervisor", route_from_supervisor, {...}) call reading whatever destination the Supervisor already wrote into state["route"], and every resolver edging back to "supervisor" rather than finishing directly — so the same confidence check applies no matter which category handled the ticket. Compiled with MemorySaver() as the checkpointer and exported as the module-level orchestrator.

The resolver tool-calling loop

Since create_react_agent is off the table, each resolver hand-rolls its own bounded loop, capped at MAX_TOOL_ITERATIONS = 4:

  1. Bind the resolver's allowed tools to the model — model.bind_tools(...).
  2. Invoke. If the response carries tool_calls, execute each one and append the results as ToolMessages; repeat.
  3. Once the model stops requesting tools (or the cap is hit — a nudge message asks it to answer with what it has), one final model.with_structured_output(ResolverOutput) call produces the answer contract.
class ResolverOutput(BaseModel):
    response: str                # customer-facing draft
    cited_article_ids: list[str] # knowledge-base grounding
    confidence: float            # 0.0-1.0
    escalate: bool
    escalation_reason: str | None
Tool identity binding

A few tools need context — the customer's external_user_id, or the internal user_id for memory — that an LLM should never be trusted to supply itself. _TOOL_BUILDERS maps each logical tool name to a closure-builder that reads that context from graph state at call time and returns a ready-to-call StructuredTool. The LLM only ever sees parameters that are actually its choice to make: query, action, tier, experience_id — never internal ids.

Confidence guidance

Every resolver's prompt carries the same rule: confidence ≥ 0.75 only when the answer is directly grounded in a retrieved article or a successful tool call; confidence < 0.5 with escalate=True when no relevant article was found, a tool call failed, or the request is outside what the resolver can verify. The Supervisor's own trust threshold is CONFIDENCE_THRESHOLD = 0.6.

04 — State Schema

One TypedDict, threaded through every node

agentic/state.py defines TicketState, carried through the entire graph. Two fields use non-default reducers so that node returns append instead of overwrite: messages uses LangGraph's add_messages, and trace uses operator.add (list concatenation) — every node's {"trace": [entry]} return value accumulates into a full audit history.

class TicketState(TypedDict, total=False):
    messages: Annotated[list[BaseMessage], add_messages]   # session memory
    ticket_id: str
    account_id: str
    external_user_id: str
    channel: str
    reported_urgency: str | None
    ticket_text: str
    user_context: dict[str, Any]         # profile, subscription, history, memories
    classification: Classification        # category, urgency, sentiment, complexity...
    draft_response: str | None
    cited_article_ids: list[str]
    confidence: float | None
    escalation_needed: bool
    escalation_reason: str | None
    escalation_summary: str | None
    final_status: Literal["resolved", "escalated"]
    route: str                            # supervisor's decision this pass
    trace: Annotated[list[dict[str, Any]], operator.add]   # append-only audit trail

06 — Tools & MCP

Plain functions first, MCP as a second layer

Business logic lives in plain, typed, independently-tested Python functions. Two FastMCP servers register those same functions directly as MCP tools — mcp.tool(fn), no wrapper boilerplate, since they're already typed and documented. Every tool returns a structured contract and never raises for an expected failure:

{"ok": True,  "data": ...}
{"ok": False, "error": "<human-readable reason>"}

That contract is what lets a resolver react to a failure — lower confidence, escalate — instead of the whole graph crashing on a bad lookup.

MCP is a parallel interface, not the resolver's path

The resolver nodes call the plain tool functions directly (via the _TOOL_BUILDERS closures in §03) — not through the MCP layer. A stdio MCP round-trip would add latency for zero benefit when the caller is already in-process. The MCP servers exist so the same tools are reachable by any other MCP-speaking client, and are exercised directly via an in-process fastmcp.Client in the test suite (no subprocess needed).

Validation examples worth calling out

manage_subscription rejects unknown actions/tiers, unknown users, and users with no subscription on file. manage_reservation additionally blocks booking for a blocked account, rejects a full experience (slots_available <= 0), and rejects double-cancelling the same reservation — each a structured {"ok": False, "error": ...}, never an exception.

07 — Knowledge Retrieval (RAG)

Embeddings + cosine similarity, no vector store

Each article's title + content + tags is embedded once with text-embedding-3-small and cached in memory, keyed by account_id — the knowledge base is effectively static reference content, so re-embedding on every search would be wasted latency and cost. A search embeds the query and ranks the cached vectors by cosine similarity. No vector-store dependency was added; a 14-article corpus doesn't need one.

0.35
RELEVANCE_THRESHOLD

Gates the search tool's own relevant flag — deliberately separate from a resolver's self-reported confidence. Below this, it's treated as "no genuinely applicable article exists," a strong escalation trigger on its own.

0.60
CONFIDENCE_THRESHOLD

The Supervisor's own bar for trusting a resolver's answer enough to finalize it, rather than escalating.

4
MAX_TOOL_ITERATIONS

Bounds every resolver's tool-calling loop, so a confused model can't spin forever.

08 — Memory Systems

Three mechanisms, three different jobs

Short-term (session)

The compiled graph's own MemorySaver checkpointer, scoped by thread_id = ticket_id. Keeps conversation state alive during one ticket session, inspectable via orchestrator.get_state_history().

Long-term (cross-session)

A new customer_memory table keyed by UDA-Hub's internal user_id, not thread_id — survives across tickets and process restarts. Written by Finalize on resolution, read by Context Loader and every resolver.

Durable interaction history

Every TicketMessage/TicketMetadata write goes straight to udahub.db — the system of record, independent of LangGraph's own checkpointing.

A custom SQLite table was chosen for long-term memory over LangGraph's InMemoryStore specifically because it needs to survive a process/kernel restart — an in-memory store, by construction, doesn't. memory_type is restricted to "preference" or "resolution_summary"; recall works the same way KB search does — embed the query, rank stored vectors by cosine similarity.

10 — Logging & Tracing

Every decision, twice: in-band and out-of-band

log_event(state, node, event, **details) is called by every node and does two things with each entry: appends it to state["trace"] — in-band, inspectable per-ticket via get_state_history() without touching the filesystem — and writes it as one JSON line to logs/uda_hub_trace.jsonl — out-of-band, greppable across every ticket and session, independent of any single LangGraph run.

Every entry carries {timestamp, ticket_id, node, event, ...decision-specific details}. A resolver's entry, for example, includes its full tool_calls list — tool name, arguments, and result — so tool usage is auditable from the log alone.

12 — Testing Strategy

97 tests, no API key required

Every LLM-calling node (classifier, the resolver factory, escalation) accepts an injectable llm parameter that defaults to a lazily-constructed real ChatOpenAI — tests instead pass a FakeChatModel that duck-types only bind_tools and with_structured_output, returning scripted responses. The same pattern applies to embeddings: embed_texts(texts, embed_fn=None) takes an injectable function, so knowledge-base and memory tests use a deterministic fake embedder instead of a live call.

Tool tests

Every database-abstraction tool's validation, error handling, and {ok, ...} contract, against isolated temp SQLite databases via tmp_path + create_all() — the real seeded databases are never touched.

MCP server tests

Both FastMCP servers' tool sets and responses, exercised via an in-process fastmcp.Client — no subprocess spawned.

Agent node tests

Each node's decision logic in isolation — classification fallback, Supervisor's two-pass routing, resolver tool loops (including bounded-iteration and failed-tool-call edge cases), escalation, context assembly, finalize's memory-write gating.

Integration tests

The actual compiled orchestrator, invoked end-to-end through both a resolution and an escalation scenario — real tool logic, real DB writes, only the LLM calls faked.

14 — Design Decisions

Why it's built this way

Hand-built graph, not create_react_agent

Explicit project requirement: every node, edge, and routing decision must be visible in code, not delegated to a prebuilt helper — langgraph_supervisor is installed but deliberately unused.

Rule-based Supervisor, not an LLM

The Classifier is already forced via structured output to commit to one category. Routing off that is a table lookup and a threshold check — adding an LLM call there would only add latency and a new failure mode for zero benefit.

No vector database

14 articles fits comfortably in an in-memory, per-account embedding cache. A dedicated vector store would be infrastructure the corpus doesn't need yet.

Custom memory table, not InMemoryStore

Long-term memory has to survive a process/kernel restart by definition — an in-memory store can't do that, so a real SQLite table with a JSON-encoded embedding column was used instead.

One resolver factory, five instances

All five category resolvers are identical in execution shape — bind tools, loop, structured output. Only the prompt and tool subset differ, so that's the only thing that varies per instance.

MCP as a parallel surface

Built to satisfy the project's MCP recommendation and make tools available to any MCP client — but the in-process resolver loop bypasses it, since a stdio round-trip buys nothing when caller and callee already share a process.
